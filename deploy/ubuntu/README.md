# Ubuntu deployment with Docker and local file storage

This deployment runs the API and built web app in one Docker container. Uploaded file bytes are kept in a persistent host directory mounted into that container; PostgreSQL stays installed on the Ubuntu host. Caddy runs on Ubuntu and provides HTTPS. MinIO is not used.

## Requirements and DNS

- Ubuntu 22.04 or 24.04, a public server address, Docker Engine with the Compose plugin, Git, and Caddy.
- Create A records for `consultwithlawyer.in` and `www.consultwithlawyer.in` pointing to the server's public IPv4. `www` can instead be a CNAME to the apex.
- Add AAAA records only if the server has working public IPv6; remove stale AAAA records.
- Allow inbound TCP 80 and 443 and SSH from trusted addresses. Do not expose PostgreSQL (5432) or the app (8080) to the internet.
- The commands below expect the repository at `/opt/legal-connect`.

Install Docker Engine and Compose using [Docker's official Ubuntu instructions](https://docs.docker.com/engine/install/ubuntu/). Install Caddy using the [official Ubuntu package instructions](https://caddyserver.com/docs/install#debian-ubuntu-raspbian).

## 1. Get the application

For a new checkout:

```sh
sudo mkdir -p /opt
sudo git clone --branch main https://github.com/Anudeep28/Legal_Connect.git /opt/legal-connect
sudo chown -R "$USER":"$USER" /opt/legal-connect
cd /opt/legal-connect
```

If `/opt/legal-connect` already contains the repository, do not clone over it. Fetch and review the desired `main` commit.

## 2. Create the PostgreSQL database

PostgreSQL can remain on the host and bound to localhost. The app container uses Linux host networking so its `127.0.0.1` database URL reaches this local PostgreSQL instance; the API itself also listens only on `127.0.0.1:8080`.

Create a dedicated role and database:

```sh
sudo -u postgres psql
```

At the `psql` prompt:

```sql
CREATE ROLE consultwithlawyer LOGIN;
\password consultwithlawyer
CREATE DATABASE consultwithlawyer OWNER consultwithlawyer;
\q
```

The `\password` command prompts without placing the password in SQL history. For the `DATABASE_URL`, a 64-character value generated by `openssl rand -hex 32` is URL-safe.

Before changing a database that already contains data, make a protected backup:

```sh
set -o pipefail
sudo install -d -m 700 /var/backups/consultwithlawyer
BACKUP="/var/backups/consultwithlawyer/before-schema-$(date +%F-%H%M%S).dump"
sudo -u postgres pg_dump -Fc consultwithlawyer | sudo tee "$BACKUP" >/dev/null
sudo chmod 600 "$BACKUP"
sudo pg_restore --list "$BACKUP" >/dev/null
```

A new empty database has no app records to back up. Applying the schema does not import Replit records, Clerk accounts, or uploaded files.

## 3. Configure private environment files

Copy the examples from the repository to `/etc`, then edit them there. Do not put populated secrets in Git:

```sh
sudo install -d -m 0750 /etc/consultwithlawyer
sudo cp /opt/legal-connect/deploy/ubuntu/app.env.example /etc/consultwithlawyer/app.env
sudo cp /opt/legal-connect/deploy/ubuntu/frontend-build.env.example /etc/consultwithlawyer/frontend-build.env
sudo chmod 600 /etc/consultwithlawyer/*.env
sudoedit /etc/consultwithlawyer/app.env
sudoedit /etc/consultwithlawyer/frontend-build.env
```

In the Clerk Dashboard, create or select the production instance and use its production `pk_live_...` and `sk_live_...` keys, not development/test keys. Set:

- In `app.env`: `DATABASE_URL=postgresql://consultwithlawyer:<URL-safe-password>@127.0.0.1:5432/consultwithlawyer`, `APP_PUBLIC_URL=https://consultwithlawyer.in`, `CLERK_PUBLISHABLE_KEY`, and `CLERK_SECRET_KEY`.
- In `frontend-build.env`: `VITE_CLERK_PUBLISHABLE_KEY` and `VITE_CLERK_PROXY_URL=https://consultwithlawyer.in/api/__clerk`.

The publishable key is included in the browser build; it is not a secret. Keep the Clerk secret key only in `app.env`. Configure the production sign-in redirects and any OAuth provider credentials in Clerk. Production Clerk starts without the development instance's users; migrate those separately if needed. Follow Clerk's [production deployment guide](https://clerk.com/docs/deployments/overview), and add any DNS verification records Clerk explicitly gives you.

The example keeps Twilio calls, call recording, SMS verification, email, and push disabled until their production settings have been configured and tested. Keep recording disabled unless both call participants have given the required consent.

## 4. Prepare persistent file storage

The API container runs as UID/GID `10001`. Create a private host directory owned by that ID:

```sh
sudo install -d -o 10001 -g 10001 -m 0700 /srv/consultwithlawyer/uploads
```

`docker-compose.yml` bind-mounts this directory at `/var/lib/legal-connect/objects` inside the container. Recreating the container will not remove the uploaded files. Do not store uploads in the container's writable layer or expose this directory directly through Caddy.

## 5. Build the Docker image and apply the schema

Build with the public Clerk settings:

```sh
cd /opt/legal-connect
sudo docker compose \
  --env-file /etc/consultwithlawyer/frontend-build.env \
  -f deploy/ubuntu/docker-compose.yml build app
```

After the database backup, apply the schema using the built image and its `app.env` database URL:

```sh
sudo docker compose \
  --env-file /etc/consultwithlawyer/frontend-build.env \
  -f deploy/ubuntu/docker-compose.yml \
  run --rm --no-deps app pnpm --filter @workspace/db run push
```

Review Drizzle's proposed changes. Do not use `push-force` as a routine deployment command.

## 6. Configure HTTPS and start the app

Install the supplied Caddy configuration, validate it, and reload Caddy:

```sh
sudo cp /opt/legal-connect/deploy/ubuntu/Caddyfile /etc/caddy/Caddyfile
sudo caddy validate --config /etc/caddy/Caddyfile
sudo systemctl reload caddy
```

Caddy obtains HTTPS certificates for the apex domain and redirects `www` to the apex. It proxies traffic to the API container, which serves both the API and the built web app.

Start the app:

```sh
cd /opt/legal-connect
sudo docker compose \
  --env-file /etc/consultwithlawyer/frontend-build.env \
  -f deploy/ubuntu/docker-compose.yml up -d
```

Check status and logs:

```sh
sudo docker compose --env-file /etc/consultwithlawyer/frontend-build.env -f deploy/ubuntu/docker-compose.yml ps
sudo docker compose --env-file /etc/consultwithlawyer/frontend-build.env -f deploy/ubuntu/docker-compose.yml logs --tail=100 app
curl -fsS https://consultwithlawyer.in/api/healthz
curl -fsS https://consultwithlawyer.in/api/readyz
```

Then test production Clerk sign-in, create a test consultation, upload and download an attachment as its client and lawyer, and verify another account is denied.

## Where data is stored

- Uploaded attachment bytes: `/srv/consultwithlawyer/uploads` on the Ubuntu host.
- Attachment names, ownership, permissions, and status: PostgreSQL.
- Twilio recording inventory, consent, transcript words, and processing status: PostgreSQL.
- Raw Twilio call audio: the current workflow fetches it for transcription and deletes it from Twilio after processing; it is not archived on local disk.
- Generated document drafts and deliverable text: PostgreSQL. They are not generated as stored files by this app.

If you later want to retain raw Twilio audio on disk, that is a separate code and retention-policy change. The inventory metadata should remain in PostgreSQL because it is queried and updated as structured records.

## Backups and updates

Back up both PostgreSQL and the uploads directory, and keep encrypted copies off this server. A same-server snapshot is not an off-server backup. For example, make a protected archive of uploads with:

```sh
sudo tar -C /srv/consultwithlawyer -czf /var/backups/consultwithlawyer/uploads-$(date +%F-%H%M%S).tar.gz uploads
sudo chmod 600 /var/backups/consultwithlawyer/uploads-*.tar.gz
```

For updates, fetch and review the intended `main` commit, rebuild with the same Clerk build environment, back up PostgreSQL before any schema change, apply schema updates with the one-off `docker compose run` command above, then run `docker compose up -d`. Verify the health endpoints and upload/download flow before considering the update complete.

Files and database records from Replit do not transfer automatically. Existing attachment rows that point to Replit storage will not resolve on this local-volume deployment unless the old file objects are separately copied and their database paths migrated.
